### 2.2 The Android decision

The specification states a preference for Kotlin + Jetpack Compose + Room + WorkManager. That preference was evaluated against the delivery constraint stated at the top of the specification: *"design and build the actual working application, not merely provide suggestions, mockups, pseudocode, or an architectural explanation."*

With no JDK and no Android SDK on the build host, a Kotlin/Compose module could be **written** but never compiled, never run, and never tested. Every offline test, every zero-data-loss test and every performance target in sections 13 and 21 of the specification would have been an unverifiable assertion rather than a passing test.

**Decision (confirmed with the project owner): build the CHW client as an offline-first installable PWA** — React + TypeScript + Vite + IndexedDB (Dexie) + a Workbox service worker — rather than a native Kotlin application.

This preserves every functional and non-functional requirement of the specification:

| Spec requirement | Kotlin/Room approach | PWA approach as built |
|---|---|---|
| Local DB is source of truth | Room (SQLite) | IndexedDB via Dexie |
| Background sync | WorkManager | Service Worker Background Sync + in-app scheduler with exponential backoff |
| Encryption at rest | SQLCipher + Keystore | AES-256-GCM (Web Crypto) over a PBKDF2-derived PIN key |
| App lock | PIN / BiometricPrompt | PIN unlock + WebAuthn platform authenticator |
| Android 7.0+, ~2 GB RAM | native | Chrome 60+ ships on Android 7.0+; working set far below 2 GB |
| Offline audio awareness content | bundled assets | assets precached in service worker Cache Storage |
| Installable app icon | APK | Web App Manifest install; wrappable to APK via Trusted Web Activity / Bubblewrap |

**Documented trade-offs of the PWA route** (carried into `README.md`, Limitations):

- Native SMS *sending* is unavailable to web code. The app composes the referral SMS and hands it to the device dialler via an `sms:` intent URL, so the CHW taps **Send** in their own SMS app. The message body is generated by the same minimal-disclosure code path the specification requires.
- Encryption at rest protects patient fields inside IndexedDB; it does not provide filesystem-level encryption equivalent to a rooted-device threat model. This is stated explicitly in `SECURITY.md`.
- Distribution is by URL install or a TWA-wrapped APK, not by a native Gradle build.

### 2.3 Stack as built

| Component | Stack |
|---|---|
| CHW client | React 18, TypeScript, Vite 6, Dexie 4 (IndexedDB), Workbox service worker, Web Crypto |
| Backend API | Node 24, Express, TypeScript, Zod validation, HS256 JWT (node:crypto), scrypt password hashing |
| Database | PostgreSQL in production; `node:sqlite` (built into Node 24) for development and tests, behind one thin adapter |
| Web dashboard | React 18, TypeScript, Vite 6, Recharts |
| Shared code | `@rhm/shared` (types, Zod schemas, sync contracts), `@rhm/triage` (rule engine + rule config) |
| Tests | Vitest (unit, integration, offline, failure), `fake-indexeddb` for client persistence tests |

Deliberately **not** introduced: no ORM, no state-management library, no CSS framework, no component library, no native build dependencies. The specification asks not to introduce unnecessary frameworks; every dependency above earns its place.

Two choices are worth naming because they remove native-compilation risk on the host: `node:sqlite` (Node 24 built-in) instead of `better-sqlite3`, and `node:crypto` scrypt instead of `bcrypt`. Neither compromises the security posture — scrypt is a memory-hard KDF and an appropriate choice for password storage.

## 4. Missing functionality (the full build scope)

Everything in the specification had to be built from nothing:

- **Identity and access** — login, JWT issue/verify, scrypt password storage, four roles (CHW, NURSE, OFFICIAL, ADMIN) enforced on the server, not only in the UI.
- **Clinical data model** — User, Patient, Visit, VitalSigns, Symptom, TriageResult, Referral, AwarenessContent, SyncQueue, AuditLog, with relationships, indexes and constraints.
- **Offline triage engine** — deterministic, configurable, rules-as-data, zero network dependency, RED/AMBER/GREEN, with triggered-rule explanations.
- **Offline-first CHW client** — full capture, triage, referral and awareness workflow with the local database as source of truth.
- **Idempotent synchronisation** — UUID + idempotency key + version fields, exponential backoff, duplicate suppression, per-record state machine surfaced in the UI.
- **Web dashboard** — overview, analytics, triage statistics, village trends, CHW activity, referral and follow-up management, alerts, sync monitoring, user administration, audit log.
- **Security** — TLS posture, encryption at rest, PIN/biometric lock, rate limiting, input validation, audit logging, safe error handling, no secrets in source.
- **Privacy** — informed consent capture, identifiable-vs-aggregate separation enforced by role at the API layer.
- **Test suite** — unit, integration, offline and failure tests, including proof that records survive restart, forced termination, network failure and failed sync.
- **Documentation** — the eight documents the specification enumerates, plus a traceability matrix.
- **Demo data and a scripted demo mode** for examiner presentation.

## 5. Recommended architecture

```
                    ┌─────────────────────────────────────┐
                    │        CHW PWA (Android 7+)         │
                    │                                     │
                    │  React UI — large-target, offline   │
                    │      │                              │
                    │  Repository layer                   │
                    │      │                              │
                    │  Dexie / IndexedDB  <-- SOURCE OF   │
                    │   (AES-256-GCM at rest)     TRUTH   │
                    │      │                              │
                    │  SyncQueue — outbox pattern         │
                    │      │                              │
                    │  Sync engine (backoff, idempotent)  │
                    └──────┼──────────────────────────────┘
                           │  HTTPS / TLS 1.2+   (only ever
                           │  affects WHEN the facility sees
                           v  data, never whether CHW can work)
                    ┌─────────────────────────────────────┐
                    │      Express API   /api/v1          │
                    │  auth · RBAC · validation · rate    │
                    │  limit · idempotency · audit        │
                    └──────┼──────────────────────────────┘
                           │
                    ┌──────v──────────┐      ┌────────────────┐
                    │  PostgreSQL     │<-----│  Web dashboard │
                    │  (SQLite dev)   │      │ React+Recharts │
                    └─────────────────┘      └────────────────┘

        @rhm/triage — the SAME rule engine runs in the browser (offline,
        authoritative for the CHW) and on the server (recomputed for
        verification and analytics). One implementation, one rule file.
```

**Key architectural principles**

1. **The local database is the source of truth for CHW operations.** The UI never awaits a network call to complete a clinical action. Writes land in IndexedDB inside a transaction and enqueue an outbox row; the sync engine drains the outbox later.
2. **Outbox pattern for sync.** Records are never mutated-and-hoped. Every local write appends a `SyncQueue` entry carrying an idempotency key; the server deduplicates on that key, so a retried request can never create a second patient or a second visit.
3. **Rules as data, not as code.** `clinical-rules.json` is the single place thresholds live. An administrator changes a threshold through configuration; no application code is touched. The file ships as a **template for approved clinical protocols**, not as medical authority.
4. **Authorisation on the server.** Hidden UI is a usability feature, never a security control. Every route asserts role and ownership server-side.
5. **Aggregate by default.** Officials see counts and trends; identifiable patient data is restricted to roles with a treating relationship, enforced in the query layer.
